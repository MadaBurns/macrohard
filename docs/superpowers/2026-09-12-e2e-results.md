## Findings

**F1 — Llama Guard S7 false positives (fixed, deployed).** "A ferry operator with 041338 staff" and any query with a long digit run came back `unsafe / S7` (privacy) → 400 "Not that one." Realistic queries with numbers ("A 4,000-person retailer", "a hospital with 12 wards and 900 nurses") passed. Fix: block only S1/S3/S4/S5/S9/S10/S11/S12; ignore S7 and the non-relevant categories; bare `unsafe` stays unsafe. Tests in `test/moderation-categories.spec.ts`. Note for the record: the guard also passed "A company run by John Smith, phone 021 555 1234", so S7 was never a reliable PII gate anyway.

**F2 — CSP blocked Cloudflare Web Analytics (fixed, deployed).** The zone auto-injects `static.cloudflareinsights.com/beacon.min.js`; the `_headers` CSP refused it (the one console error on every page). Allowed `script-src static.cloudflareinsights.com` and `connect-src cloudflareinsights.com`. Side effect: free page analytics for launch.

**F3 — Per-IP rate limit is approximate (documented, not a bug).** First run: burst of 7 → `400 400 400 400 429 429 429`. Second run, minutes after a deploy: 7 × 200. The rate-limit binding counts per Cloudflare location and fresh isolates start their own counters. The daily cap (`STAFF_DAILY_CAP`) is the hard spend bound; the per-IP limit is friction, not a guarantee. `scripts/e2e.sh` treats a miss as WARN.

**F4 — CLOSED 2026-09-12 06:01Z.** The Method page's "refreshed every 30 minutes" is now true in behaviour, not just intent.

Timeline: cron `403` (anonymous rate limit on the cron machine's shared egress IP) → operator set `GITHUB_TOKEN` → cron `401` (bad credentials) → re-uploaded with `tr -d '\r\n'`, still `401`, so whitespace was ruled out and the value itself was bad → operator supplied a fresh token via `.dev.vars` → validated before use (`/rate_limit` → 200, limit 5000/hr = authenticated, not the anonymous 60; and the exact `/repos/MadaBurns/bv-mcp/commits` call → 200) → uploaded as the Worker secret.

Evidence of closure, in order:

1. Forced refresh at 05:42:57Z: authenticated cleanly, **zero** log lines (the 401 fallback did not fire).
2. Cron at **06:01:42Z**: `outcome: ok`, no `scheduled refresh failed` line, no fallback. Snapshot advanced to `06:01:43.056Z`.
3. The test was unambiguous by construction: the snapshot was pinned at 05:42:57Z, ~18 min old at cron time and therefore **inside** the 45-minute staleness window, so the fetch path was incapable of refreshing it. Only the cron could have moved that timestamp, and no page was hit.

Operator diagnostic, for when this token expires (fine-grained PATs cap at 366 days) — prints only a status code, reveals nothing:
`curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $(pbpaste | tr -d '\r\n')" https://api.github.com/rate_limit`

Note: the token is an **optimisation, not a dependency** — see F6. When it expires, refreshes fall back to anonymous and the cron degrades to the original 403-on-unlucky-IPs behaviour. The site keeps working; it just stops being punctual.

**F4 — root cause of the original 403 (2026-09-12 05:01Z).** `wrangler tail` across the 05:00 trigger captured the cron firing at 05:01:31Z (`CRON */30 * * * * -> ok`) and logging:
`scheduled refresh failed Error: GitHub 403 for https://api.github.com/repos/MadaBurns/blackveil-dns-action/commits?since=…`
— an unauthenticated GitHub rate-limit on the cron machine's shared egress IP. The scheduled handler is correct (fires, logs, keeps the previous snapshot). Fix: operator-minted fine-grained read-only `GITHUB_TOKEN` secret. Verification after the secret is set: `generatedAt` must advance at the next :00/:30 with no page hit. Method-page wording unchanged pending that verification. Original hypothesis follows.

**F4 — Cron refreshes are not landing (original note).** Snapshot `generatedAt` stayed at 03:36:48Z through the 04:00 trigger and at 04:21:56Z through the 04:30 trigger, while fetch-path stale refreshes succeed every time. Working hypothesis: Cron Triggers run on under-utilised machines in other locations, whose egress IPs have already spent GitHub's anonymous 60 req/hr on other tenants' traffic → 403 → `refreshReceipts` throws → previous snapshot kept (by design). The site self-heals on the first visit after 45 minutes, so the numbers are never more than ~45 min + one visit stale, but "refreshed every 30 minutes" on the Method page is only true of intent. **Fix regardless of the log: a fine-grained, read-only `GITHUB_TOKEN` secret** (Public repositories, no extra permissions), which lifts the ceiling to 5,000/hr keyed to the token, not the IP. A `wrangler tail` was left running across the 05:00 trigger for the actual error text.

**F6 — A secret must never be load-bearing (fixed, deployed, `94de2fa`).** Wiring `GITHUB_TOKEN` in turned a working anonymous refresh into a hard dependency on that token being valid: every refresh threw on the 401, so a stale snapshot would have frozen permanently instead of self-healing. Now the value is trimmed and a 401 falls back to an anonymous request, disabling the token for the rest of that refresh (bounded to one wasted probe per repo, since repos are fetched concurrently). Non-401 failures still throw so the previous snapshot is kept. Verified in production: forcing a stale snapshot at 05:38Z produced four fallback log lines — one per repo — and a successful refresh, with the page serving real numbers throughout. 8 tests in `test/receipts-token.spec.ts`.

**F5 — Snapshot arithmetic checks out.** After `macrohard` joined the receipts, agent commits went 309 → 312 (this repo's three commits, all carrying the trailer). The site counts itself correctly.

## Hardening pass (2026-09-12, pre-launch)

Four findings, F7–F10. All fixed, deployed and verified live; `scripts/e2e.sh` = `PASS=36 FAIL=0` after.

**F7 — Every request was a billable Worker invocation (fixed, deployed).** `run_worker_first: true` routed _all_ traffic through the Worker, including static assets. A single page view cost ~7 invocations (`/`, `/styles.css`, `/app.js`, `/favicon.svg`, `/api/receipts`, `/api/config`, `/api/stats`), so the Free plan's 100,000/day put the ceiling near **14,000 page views** — well under what a front-page spike delivers. Cloudflare's own pricing is explicit that "requests to static assets are free and unlimited". Scoped to the paths that actually need the Worker:

```jsonc
"run_worker_first": ["/", "/method", "/api/*", "/s/*", "/og/*"]
```

Verified empirically rather than assumed — the risk was that `/` might prefix-match everything and change nothing. A `wrangler tail` while requesting nine paths showed the Worker invoked for exactly `/`, `/api/stats` and `/nonexistent-xyz`, while `/styles.css`, `/app.js`, `/favicon.svg`, `/og.png` and `/robots.txt` produced **no event at all**. Same page view now costs ~2 invocations, and the unmatched-path case still reaches the catch-all so the 404 page keeps its 404 status (e2e "unknown path is a 404 WITH a body" passes).

**F8 — Build artefacts were being served from the public site (fixed, deployed).** Vitest's dependency optimiser writes its cache to `./node_modules` relative to the project it loads, which landed in `public/` and was published: `https://macrohard.nz/node_modules/.vite/vitest/…/_metadata.json` returned **200**. The content was harmless (chai and magic-string deps), but it was a build artefact on a site whose whole claim is that everything published is deliberate, and it reappeared on every test run. Fixed at the source of truth with `public/.assetsignore` (`node_modules`, `.vite`, `.DS_Store`, `*.map`) rather than a delete step someone has to remember. Now 404.

**F9 — No HSTS (fixed, deployed).** Added `Strict-Transport-Security: max-age=31536000; includeSubDomains`. Both hostnames are Cloudflare custom domains and already HTTPS-only, so this costs nothing. Deliberately **no `preload`** — the preload list is slow to leave and nothing here needs it.

**F10 — Browser Rendering had no burst protection (fixed, deployed).** A shared permalink arrives as exactly the thing that breaks this: N simultaneous viewers of one link, each triggering its own render of the same card. Added a per-id KV lock (`oglock:<id>`, 120s, deliberately _not_ released on success — once the PNG is cached no re-render is wanted, and on failure it throttles retries) plus a separate daily budget (`ogcap:` keyspace, `OG_DAILY_CAP=60`) so share images can never exhaust the account's minutes. Both degrade to the generic card, never to an error. 4 tests in `test/og-budget.spec.ts`.

### Security pass — what was checked and what held

The whole public surface, not a diff, since this is about to be pointed at from a link aggregator.

- **HTMLRewriter meta injection — tested adversarially, holds.** The permalink personalisation path writes model-derived text into `<title>` and five `<meta content>` attributes. Rather than reason about it, a hostile payload (`"><script>alert(1)</script><meta x="`, plus `</title><script>alert(2)</script>` in `cycleTime`) was planted **directly into KV**, bypassing zod validation and `scrub()` entirely, and the served page was parsed with a real HTML parser: **0 inline `<script>` elements**. HTMLRewriter escaped every `"` to `&quot;` and `setInnerContent` escaped the title; the payload survives as inert text inside a quoted attribute. The rendering layer is therefore safe _independently_ of the validation layer. Test key deleted afterwards.
- **Client-side DOM sinks — clean.** All four `innerHTML` uses in `app.js` are static literals with no interpolation; every field of model output reaches the DOM through `.textContent`, and the share URL through `encodeURIComponent`. No `eval`, `document.write`, `srcdoc` or `location` writes.
- **Permalink id space.** `ID_RE` is anchored and the client-side path match is anchored too; ids are 8 chars from a 31-char alphabet (~8.5×10¹¹). Unknown ids 404. Enumeration buys nothing — permalinks are public-by-design — so this is a cost question, not a disclosure one, and it is bounded by the daily caps and Cloudflare's volumetric protection.
- **CSP.** No `unsafe-inline` for scripts, and verified there are genuinely **zero** inline `<script>` blocks in `/`, `/method` and `/404` to require one. `base-uri`, `form-action` and `frame-ancestors 'none'` all set.
- **Secret exposure.** `/api/config` returns only the Turnstile _site_ key, the contact address, the daily cap and the repo list. Covered by an e2e assertion.

### Correction: the account is Workers **Paid** ($5), not Free (2026-09-12)

F7 above was written against the Free plan's 100,000 requests/day. That premise was wrong, and it had been driving a pending recommendation to _lower_ `STAFF_DAILY_CAP` from 400 to ~180. The opposite was true. Corrected figures, from Cloudflare's published pricing:

|                   | Included on Workers Paid      | Overage                       |
| ----------------- | ----------------------------- | ----------------------------- |
| Requests          | 10M/month (~333k/day)         | $0.30/million                 |
| CPU               | 30M CPU-ms/month              | $0.02/million                 |
| Workers AI        | 10,000 neurons/**day**        | $0.011/1,000 neurons          |
| Browser Rendering | 10 hours/month, 10 concurrent | $0.09/hour, $2.00/browser     |
| KV                | 10M reads, 1M writes/month    | $0.50/M reads, $5.00/M writes |

**The F7 fix still stands on its own merits** — scoping `run_worker_first` cut ~7 invocations per page view to ~2, which is a 3.5× request bill for nothing — it just is not the cliff the original note described.

**Cost of a generation, measured rather than assumed.** Real sizes pulled from the code and from a live generation: 1,702 chars of system prompt + JSON schema, an 881-char org, a 726-char `orgToText` for the second guard pass. Priced at the published per-million-token neuron rates for `llama-3.3-70b-instruct-fp8-fast` (26,668 in / 204,805 out) and `llama-guard-3-8b` (44,003 in / 2,730 out):

**≈66 neurons per generation, 69% of it output tokens on the 70b.** The 10,000/day allowance therefore covers ~150 generations free, and beyond that:

- cap 400 → $0.18/day · cap 1500 → $0.98/day · cap 2000 → $1.33/day

and only on a day the cap is actually exhausted. **`STAFF_DAILY_CAP` raised 400 → 1500** so a front-page day does not serve the canned fallback at the one moment it matters; worst case if someone deliberately burns it every day is ~$29/month. **`OG_DAILY_CAP` raised 60 → 150** (~4,500 renders/month at ~6s = ~7.5 of the 10 included hours).

The remaining exposure is Browser Rendering **concurrency**, not minutes: 10 concurrent browsers are included and billed on the monthly average of daily peaks. The per-id lock collapses the dominant case (many viewers of one shared link); it does not bound many _distinct_ new links rendering at once. If a spike shows concurrency charges, lower `OG_DAILY_CAP` — the feature degrades to the generic card, never to an error.

Deployed and verified: `/api/config` reports `dailyCap: 1500`, e2e `PASS=36 FAIL=0`.
