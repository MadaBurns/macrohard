## Findings

**F1 — Llama Guard S7 false positives (fixed, deployed).** "A ferry operator with 041338 staff" and any query with a long digit run came back `unsafe / S7` (privacy) → 400 "Not that one." Realistic queries with numbers ("A 4,000-person retailer", "a hospital with 12 wards and 900 nurses") passed. Fix: block only S1/S3/S4/S5/S9/S10/S11/S12; ignore S7 and the non-relevant categories; bare `unsafe` stays unsafe. Tests in `test/moderation-categories.spec.ts`. Note for the record: the guard also passed "A company run by John Smith, phone 021 555 1234", so S7 was never a reliable PII gate anyway.

**F2 — CSP blocked Cloudflare Web Analytics (fixed, deployed).** The zone auto-injects `static.cloudflareinsights.com/beacon.min.js`; the `_headers` CSP refused it (the one console error on every page). Allowed `script-src static.cloudflareinsights.com` and `connect-src cloudflareinsights.com`. Side effect: free page analytics for launch.

**F3 — Per-IP rate limit is approximate (documented, not a bug).** First run: burst of 7 → `400 400 400 400 429 429 429`. Second run, minutes after a deploy: 7 × 200. The rate-limit binding counts per Cloudflare location and fresh isolates start their own counters. The daily cap (`STAFF_DAILY_CAP`) is the hard spend bound; the per-IP limit is friction, not a guarantee. `scripts/e2e.sh` treats a miss as WARN.

**F4 — RESOLVED CAUSE (2026-09-12 05:01Z).** `wrangler tail` across the 05:00 trigger captured the cron firing at 05:01:31Z (`CRON */30 * * * * -> ok`) and logging:
`scheduled refresh failed Error: GitHub 403 for https://api.github.com/repos/MadaBurns/blackveil-dns-action/commits?since=…`
— an unauthenticated GitHub rate-limit on the cron machine's shared egress IP. The scheduled handler is correct (fires, logs, keeps the previous snapshot). Fix: operator-minted fine-grained read-only `GITHUB_TOKEN` secret. Verification after the secret is set: `generatedAt` must advance at the next :00/:30 with no page hit. Method-page wording unchanged pending that verification. Original hypothesis follows.

**F4 — Cron refreshes are not landing (original note).** Snapshot `generatedAt` stayed at 03:36:48Z through the 04:00 trigger and at 04:21:56Z through the 04:30 trigger, while fetch-path stale refreshes succeed every time. Working hypothesis: Cron Triggers run on under-utilised machines in other locations, whose egress IPs have already spent GitHub's anonymous 60 req/hr on other tenants' traffic → 403 → `refreshReceipts` throws → previous snapshot kept (by design). The site self-heals on the first visit after 45 minutes, so the numbers are never more than ~45 min + one visit stale, but "refreshed every 30 minutes" on the Method page is only true of intent. **Fix regardless of the log: a fine-grained, read-only `GITHUB_TOKEN` secret** (Public repositories, no extra permissions), which lifts the ceiling to 5,000/hr keyed to the token, not the IP. A `wrangler tail` was left running across the 05:00 trigger for the actual error text.

**F5 — Snapshot arithmetic checks out.** After `macrohard` joined the receipts, agent commits went 309 → 312 (this repo's three commits, all carrying the trailer). The site counts itself correctly.
